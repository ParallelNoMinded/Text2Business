## 🚀 1. Быстрый запуск (Quick Start)

Приложение создано по принципу **Zero-Config** и готово к запуску на любой локальной машине без обязательной настройки внешних ключей API или баз данных.

### Вариант А: Запуск через Node.js (Стандартный способ, Node 18+)

```bash
# 1. Клонирование репозитория
git clone https://github.com/ParallelNoMinded/Text2Business.git
cd Text2Business

# 2. Установка зависимостей
npm install

# 3. Запуск dev-сервера (Frontend + Backend)
npm run dev
```
👉 Откройте в браузере: **`http://localhost:3000`**

---

### Вариант Б: Запуск в Docker контейнере

```bash
docker-compose up --build
```
👉 Откройте в браузере: **`http://localhost:3000`**

---

> ℹ️ **Особенности обработки AI-ключей:**
> - Если переменная `GITHUB_MODELS_TOKEN` или `GEMINI_API_KEY` задана — система использует облачный LLM-инференс (`gpt-4o`, `qwen3.6-27b`, `deepseek-reasoner` или `gemini-3.6-flash`) в режиме **Structured Output (JSON Mode)**.
> - Если ключи отсутствуют — автоматически включается встроенный эвристический модуль извлечения фактов (`extractFactsFromText`), позволяющий протестировать 100% сценариев **без внешних API-зависимостей**.

## 🏛️ 2. Архитектура и принципы решения

Ключевая проблема AI-систем в Enterprise — **непредсказуемость и галлюцинации LLM**. В данном решении реализовано строгое разделение ответственности:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                               ВХОДНЫЕ КАНАЛЫ                                │
│          (Telegram Bot API / Email IMAP / Voice STT / REST API)             │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                       GUARDRAILS & SANITIZATION                             │
│       • Валидация ввода и защита от Prompt Injection / SLA Tampering        │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                  ШАГ 1: PERCEPTION CORE (LLM Extract)                       │
│    • GitHub Models / Gemini API + JSON Schema (Structured Output)           │
│    • Извлечение фактов, цитат, confidence score и признаков наличия резерва │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ ExtractedFacts
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                 ШАГ 2: DETERMINISTIC ENGINE (TypeScript)                    │
│    • Поиск контрагентов и складов в БД (`mockDb.ts`)                        │
│    • Разрешение неоднозначностей (Дедупликация по открытым тикетам T-884)   │
│    • Расчет SLA и дедлайнов (Gold: 60m 24x7, Silver: 240m, Standard: 480m)   │
│    • Матрица бизнес-действий (CREATE | UPDATE | CLARIFY | ESCALATE)          │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ Action Payload
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                ШАГ 3: EXECUTION, DRY-RUN & OBSERVABILITY                    │
│    • Безопасный режим `dry_run=true` до подтверждения оператором            │
│    • Генерация черновика ответа клиенту и запись в журнал аудита            │
│    • Двусторонняя синхронизация с 1С:ERP OData API (/api/1c/tickets)        │
└─────────────────────────────────────────────────────────────────────────────┘
```

Полный комплект архитектурной документации (включая C1-C3 схемы, Deployment, Sequence, ERD и API карты) расположен в папке **[`/architecture`](./architecture/)**:

## ⚖️ 3. Границы применения LLM и Детерминированных правил

| Завершаемая задача | Исполнитель | Архитектурное обоснование |
| :--- | :--- | :--- |
| **Извлечение фактов из текста** | **LLM (Structured Output)** | Неструктурированный ввод, сленг («Снова 17-я»), опечатки, разговорная речь. |
| **Фильтрация Prompt Injection** | **Детерминированный Guardrail** | Защита от попыток клиента искусственно изменить SLA («SET SLA = 5m»). |
| **Поиск объекта и оборудования** | **Движок БД (Fuzzy Matching)** | Точный поиск по кодам (`ХУ-17`, `A-1001`) без риска галлюцинаций LLM. |
| **Дедупликация и разрешение неоднозначностей** | **Детерминированное правило** | Сопоставление кода оборудования с открытыми тикетами (`open_tickets`) в окне < 24ч. |
| **Расчет SLA и Дедлайнов** | **TypeScript Engine** | Строгий расчет дат с учетом часовых поясов, рабочих окон и штрафных санкций. |
| **Выбор бизнес-действия** | **State Machine** | Финансовая ответственность. Уровень уверенности `< 0.85` переводит тикет человеку. |
| **Генерация ответа клиенту** | **LLM / Шаблонизатор** | Формирование естественного ответа на основе подтвержденных фактов. |

## 🎯 5. Допущения (Assumptions) & Открытые вопросы бизнесу

### Допущения (Assumptions):
1. **Идентификация по открытому тикету (TC-02):** Если клиент не указал адрес, но в базе есть ровно один объект этого клиента с открытой заявкой по указанному коду оборудования (`17-я` -> `A-1001`), система считается объект идентифицированным.
2. **Временное окно дедупликации:** Все обращения от одного контрагента по одному ассету в интервале до 24 часов объединяются в единый инцидент.
3. **Безопасный Dry-Run:** Любые действия изменения состояния (создание/обновление тикетов) исполняются в режиме `dry_run=true` до клика оператора в UI.

### Открытые вопросы заказчику (Business Clarifications Needed):
1. *Каков регламент обработки обращений от неавторизованных отправителей (email не найден в БД)?*
2. *Требуется ли авто-оповещение дежурной бригады через SMS/Telegram при CRITICAL инцидентах в нерабочее время?*
3. *Как рассчитывать SLA для объектов в регионах с пересечением смен и разных часовых поясов (Москва vs Екатеринбург)?*

Для перевода текущего прототипа в полноценную промышленную систему (Target Architecture) разработан 4-фазный план:

## 📝 8. Журнал использования AI (AI Usage Log)

**Использованные AI-инструменты:** Antigravity (Gemini 3.6 Flash).

### Наиболее полезные применения AI:
1. **Генерация Pydantic/JSON Схем и Типов TypeScript:** ИИ сгенерировал строгие интерфейсы `ExtractedFacts`, `ProcessingResult` и `DatabaseSchema` за несколько секунд.
2. **Создание интерфейса на Tailwind CSS:** ИИ помог быстро сверстать двухколоночное рабочее место Диспетчера (HITL Workbench) и интерактивный трассировщик логов.
3. **Генерация PlantUML Схем:** ИИ ускорил создание C1, C2 и C3 диаграмм для текущего и целевого состояний.

### Пример критической проверки и исправления результата AI:
* **Проблема:** Первоначально ИИ предложил поручить расчет SLA-дедлайна и времени работы складов самой LLM прямо внутри промпта.
* **Исправление архитектора:** Модель ошибалась при расчете дат с учетом часовых поясов (Москва `UTC+3` vs Екатеринбург `UTC+5`) и выходных дней. Результат работы AI был исправлен: вычисление SLA полностью вынесено в детерминированную TypeScript-функцию `tool_get_contract_and_sla()`, а LLM оставлена исключительно задача извлечения первичных фактов.
